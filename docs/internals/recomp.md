# How the recomp works

The internals of the native port: what the translator needs, how the host boots the game, and how the first-run ("split") build
works. For the addresses mentioned see [address-map.md](address-map.md); for the ROM releases, [versions.md](versions.md).
Labels: **[V]** verified by a script, test or by reading the code; **[I]** inference.

## 1. Pipeline

```
your dump (.z64/.n64/.v64) --hash check--> inflate the 14 code chunks (native ERZ decoder)
   --> code blob: ROM[0:0x1000] | boot segment | inflated main image       (stays on your machine)
   --> N64Recomp + the function list (recomp/thps1.syms.toml, our hooks)    --> 2,778 functions of C
   --> RSPRecomp + config/thps1.aspMain.toml                                --> the audio microcode as C++
   --> system compiler                                                      --> game library (2 MB)
engine (host + N64ModernRuntime + RT64 + SDL) loads the library and runs the game.
```

- **N64Recomp** (`ffb39cd`) translates MIPS to C from a symbol file; it builds on macOS arm64 with CMake and Ninja in about a
  minute, needing no patches. It reports **0 warnings** on our function list. [V]
- The recompiler's config (`recomp/thps1.recomp.toml`, generated per code class by `tools/gen_versions.py`) has an entry point
  `0x80000400`, three instruction patches (PS1 coprocessor-2 leftovers turned into no-ops), one ignored function, and the
  `[[patches.hook]]` blocks of `config/thps1.hooks.toml` (by function name, shared by all releases).
- N64Recomp's symbol-file mode needs the entry function at ROM `0x1000`, so the code blob is `ROM[0:0x1000]`, then the boot
  segment at blob `0x1000` and the inflated main image at blob `0x13B10`: the pattern the Conker recomp uses. [V]
- The generated C is ROM-derived. It is never committed, never shipped, and in the release it is built on the user's machine
  and deleted after the library is linked.

## 2. The function list

Generated by `decomp/common/funclist.py` and `gen_syms.py`: 2,743 functions (253 boot, 2,490 main), and the host adds 35 more
starts, listed in `decomp/common/host_force/thps1.toml`, found at run time or by rule. Strong starts: `jal` targets from both images;
data pointers to a prologue, to the instruction after a return, or to a 16-aligned address after padding; section starts; curated
symbols. Weak starts (splat labels, a sweep for returns) are dropped when an earlier function branches across them. Padding
before a 16-byte boundary is recognised as all zeros, an invalid opcode, an opcode the compiler never emits (`lld`, `pref`,
`sync`, 64-bit ALU, COP2 and similar), a use of `$k0` or `$k1`, or a jump outside code. Jump tables are runs of at least two data
pointers within 8 KB of each other. Handwritten loader code is sized by hand (a `range` in `symbols/boot.txt`).

The 35 host-added starts are real entries inside bigger parents: 31 sit inside the libmus F-command functions (the parents
`Fstop` to `Fprint`), found by the data-pointer rule (a pointer in `.data`, the F-command table at `0x800ECB48`, to just after a
return) or by the prologue rule, the first of them as the original run-time lookup miss; 3 are in the audio-thread initialiser
(prologue rule); 1 is behind an endless thread loop (a lookup miss). They are applied to the host's own copy of the symbol file, so the decomp's list and
its byte-identical rebuild are unaffected. [V]

**Completeness checks** (`decomp/common/recomp_check.py`, no emulator): every word of both text ranges lies inside a listed
function or is padding between objects. 76 of the 80 indirect jumps become `switch` statements (the other 4 are libultra's
own, which the runtime reimplements). 231 indirect-call sites go through the runtime's function lookup; every vtable slot
(86 vtables, 304 slots, 210 distinct targets) and every code pointer in data or built with `lui/addiu` is already a function
start, so a lookup miss at run time would mean a pointer computed some other way. 492 `do_break` calls come from division checks. [V]

## 3. Boot

1. librecomp's IPL3 step copies ROM `0x1000` plus 1 MiB to `0x80000400` and registers every code section whose blob offset falls
   in that range at ROM-relative addresses. That is right for the boot segment and wrong for the main image (blob `0x13B10` is
   `0x80016AC0`).
2. Our `GameEntry.entrypoint` wrapper unloads those and re-registers the main sections at `0x80016AC0`, then runs the recompiled
   `Boot_Entry`.
3. `Boot_Main` runs as recompiled code: BSS clear, `osInitialize`, the chunk-table read and the 14-chunk inflate loop, then the
   call to `GameEntry`. Its two hardware-touching leaves are hooked: `Boot_PioCopy` becomes a ROM-to-RDRAM copy, and the two ERZ
   decoders become the native decoder in `src/erz.cpp`, byte-identical to the decomp's image for all 14 chunks (`erz_selftest`).
4. The game's DMA thread (`0x800BAE84`) reads assets with `osPiRawStartDma` and waits on a cartridge event. The runtime's version
   is a fatal stub and its `osSetEventMesg` ignores those events, so both are renamed in the host symbol copy and hooked: the DMA
   copies from the ROM and posts the registered message.

The main image is thus inflated by the game's own loader, with native decoders; nothing ROM-derived has to ship besides what the
user's dump provides at run time.

## 4. The rest of the host

- **Frame pacing.** The game's scheduler thread (`0x800BC57C`) is a standard libultra-style scheduler (messages: SP = 1, DP = 2,
  retrace = 3, pre-NMI = 4), driven by the runtime's video and RSP events at a steady 30 fps. When the window is occluded,
  `CAMetalLayer.nextDrawable` blocks for about a second per present and RT64's present-to-workload chain would stall the game
  with it, so `src/macos_window.mm` watches the window's occlusion state and presents are skipped meanwhile.
- **Audio.** `n_aspMain` is translated by RSPRecomp (`config/thps1.aspMain.toml`). The audio thread produces a buffer whenever
  `osAiGetStatus` says the audio FIFO is not full; the hook reports "full" while the SDL queue holds more than 800 frames (36 ms
  at 22,050 Hz). Output was checked for level, tempo and spectrum (`tools/wav_check.py`), not for bit-exactness.
- **Edges.** The game clears its frames under a scissor whose right and bottom edges are exclusive, so one column and one row are
  never cleared and 2D drawn with a full scissor can leave pixels there. `src/dl_fixes.cpp` widens that scissor by one in each
  display list before RT64 reads it.
- **Input** (`src/input.cpp`): SDL controllers and keyboard through remappable bindings; controller state is read on the main
  thread only (a game-thread SDL call crashed sdl2-compat). **Controller Pak** (`src/pak.cpp`): the `osPfs*` file API on a real `.mpk`
  layout; `osContGetQuery` is hooked so the port reports a pak present, otherwise the game's note list closes at once.
- **Widescreen** (`src/widescreen.cpp`): the game's frustum and culling are widened (`View_SetFrustum`, `View_ComputeCullPlanes`),
  RT64 gets a patch for extended-aspect slack, and the in-level HUD goes to the screen edges by default (`src/hud_anchor.cpp`; `--hud original` keeps it centred 4:3).
  **Two players** draw two side-by-side views, each a half-width viewport and scissor (THPS1 v1.1: `View_ApplyRect` at 0x800A602C emits the
  viewport and the scissor of a view from its rect). RT64 only widens a full-width view, so a second patch widens a pair of half views, and
  each player's HUD block goes to its own view's left edge. **Frame interpolation** (`src/interpolation.cpp`):
  RT64 renders in-between frames and pairs each transform with the previous frame's; the host tells RT64 the game's rate (30) on
  every task and tags camera cuts so they are not swept. THPS1's matrices suit this: world-space model matrices that are loaded,
  never pushed, and a view-projection camera. Measured numbers: [../VERIFICATION.md](../VERIFICATION.md).
- **Patches to RT64** (`decomp/common/host/patches/`): a one-line include for recent macOS SDKs; present capture plus
  widescreen slack; frame-interpolation counters, a pre-command hook, and clearing of new colour targets (needed for MSAA in
  widescreen); widening for side-by-side split screens. They are carried as patch files and applied by `tools/setup_runtime.py` to the pinned commit.
- **PAL.** The game picks 50 or 60 Hz timing from `osTvType`. The runtime paces retraces at 60 Hz, so the host sets NTSC by
  default, including for the European release (see the [MANUAL](../MANUAL.md#why-europe-runs-at-60-hz)). A 50 Hz runtime patch (`ultramodern-vi-rate.patch`) is
  written and not applied.

## 5. The split build: no game code in the app

`-DTHPS_SPLIT_GAME_LIB=ON` builds the engine **without any recompiled game code**. On first run the app translates the user's ROM
with the bundled N64Recomp and RSPRecomp, compiles the C with the system compiler, and loads
`<config>/game/thps1_game_<class>.<dylib|so|dll>`.

- **The boundary.** The library never links against the engine. `thps_game_init` receives an array of 91 function pointers
  (`src/game_imports.def`: 77 libultra stand-ins, 11 host hooks, 4 runtime helpers), and the library defines the imported names itself
  as one-line forwarders. The same code is therefore a dylib, `.so` or DLL. A name missing from the list fails the link with the name.
- **What ships** (our code, as source compiled on the user's machine): `game-lib/game_lib.cpp` (forwarders, the section table,
  `thps_game_init`) and `game_rsp.cpp` (the RSP wrapper with private DMEM). The runtime headers the generated C includes (7 files)
  are bundled as "SDK" headers.
- **The recipe per code class** is facts only: the host symbol file (names, addresses and sizes: the same kind of data as the
  committed `recomp/thps1.syms.toml`), the recompiler config (COP2 patches, hook texts), and a fingerprint (XXH3-64) of the
  code blob **per release**, so a modified dump is refused before translating.
- **Staleness stamp:** ABI + class + hash of the bundle's resource tree + hash of the dump. An app update that changes the recipe,
  the tools or the SDK rebuilds on the next start; a library that fails to load is rebuilt once.
- **Compiler detection.** macOS: `xcode-select -p` (the one probe that does not open Apple's installer), then `xcrun`. Windows
  (later): a bundled, pinned llvm-mingw. Linux: the system clang or gcc.
- **Measured first run** (USA v1.1, 2,778 functions into 54 C files, 17 MB): find compiler 0.01 s; read and inflate 0.06 s;
  N64Recomp 0.24 s; RSPRecomp 0.01 s; compile the C 2.7 s; compile the glue and audio code 1.4 s; link 0.08 s; **4.5 s total**
  on 10 cores (1 job 18.2 s, 2 jobs 10.0 s, 4 jobs 6.0 s). `THPS_BUILD_JOBS=N` limits parallelism.
- **Findings.** (a) `RECOMP_FUNC` is a weak inline function; a strong forwarder with the same name silently overrides the game's own
  copy, so the import list must be `nm -u` of the objects minus what they define. (b) Code classes do not carry over to a first-run
  build: the static build runs v1.1's code on the European dump, but the first-run build translates the dump it is given, and the two
  code blobs differ in 230 words. Later finding (2026-10-12): only one of them is live code (the TV-type accessor); a
  `[config]` table in `versions/us11/host_force.toml` ignores two padding "functions" and pins that word, so Europe shares the
  `us11` recipe with a second fingerprint. (c) N64Recomp and RSPRecomp are 0.9 MB and 0.5 MB.
- **Bundle scan:** no run of 64 or more ROM-derived bytes ([../VERIFICATION.md](../VERIFICATION.md)).

**LiveRecomp** (`-DTHPS_LIVERECOMP=ON`, `--live-game`) is a research mode that translates the whole game in memory at start with
N64Recomp's LiveRecomp (0.20 s per start, 1.15 ms against 0.85 ms game-thread CPU per frame, suite 29/0/4). It lacks hooks with
C text (replaced by a native table), "static" functions, and, decisively, an RSP interpreter (the audio microcode needs the
compiler). It is a possible later fallback for machines without a compiler, not the release path.

## 6. Platforms

macOS (Metal) is the only system the game has been played on. The Windows and Linux support is written and built in CI with
ROM-free stand-in functions: OS seams in `src/platform.{h,cpp}` (timer resolution, UTF-8 arguments, per-user config folder, window
visibility, process spawning, library loading), `src/crash.cpp`, `create_window()` in `src/main.cpp` and the CMake file, structured
after Zelda64Recomp's `main.cpp` (credits in [NOTICE](../../NOTICE.md)). Config folders: macOS `~/Library/Application Support/THPS1-64Recomp`,
Windows `%LOCALAPPDATA%\THPS1-64Recomp`, Linux `$XDG_CONFIG_HOME` or `~/.config/THPS1-64Recomp`; a `portable.txt` beside the
executable overrides them. Graphics: Metal on macOS, D3D12 then Vulkan on Windows, Vulkan on Linux (`--api` forces one).

## 7. Building the host from source

`python3 -I decomp/thps1/recomp-host/tools/build_host.py --rom YOUR.z64` does everything: pinned runtime and RT64 plus our patches
(`tools/setup_runtime.py`), N64Recomp and RSPRecomp at the pin, a venv with rabbitizer, the code blob, `tools/gen.py`, then CMake
and Ninja (first build about 8 minutes). `--stub` builds the host with stand-in functions to check the toolchain; it cannot play.
By hand and per-option details: [the host README](../../decomp/thps1/recomp-host/README.md).
